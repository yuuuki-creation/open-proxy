## 目的

1. V2 剩余部分：上行方向和 UDP 的计量是否准确
2. V3：停用用户时，能否断开他已有的连接、拒绝新连接，且不影响同一入站上的其他人

## 做法

- 上行：`curl -X POST --data-binary @50MB` 经各协议发到流量源的 `/upload`，比对计数增量、服务端收到的字节数和文件大小
- UDP：原型内置 UDP 回显服务；新增 `udp-test` 子命令，通过 SOCKS5 的 UDP ASSOCIATE 发 500 个 1200 字节的包，比对计数
- V3：u1 和 u2 各开一个下载，`POST /disable?user=u1`，观察 u1 的计数是否停止增长、curl 是否中断、u2 是否继续；再验证停用期间的新连接和恢复后的访问
- 所有进程在 `open-proxy.slice` 内，测试期间持锁

V3，服务端按 3 MB/s 发送时停用 u1：

| 观察项 | 结果 |
| --- | --- |
| 停用返回 | `{"closed":1,"user":"u1"}` |
| u1 停用瞬间计数 | 21627003 → 最终停在 21758075（此后不再增长） |
| 停用后多收到的数据 | 约 131 KB，即一个缓冲区 |
| u1 的 curl | 收到 21757952 字节后中断 |
| u2 | 继续下载，100 秒内收到 308 MB，全程未受影响 |
| 停用期间 u1 新连接 | 被拒绝（curl 退出码 52） |
| 恢复后 | 立即可访问 |
| 连接登记 | 停用后 u1 归 0，服务端 20001 端口只剩 u2 的一条 ESTAB |

## 结论

- V2 通过：四种协议的 TCP 双向和 UDP 计量都准确，可以按「入站 × 用户」上报累计值
- V3 通过：追踪层登记连接 + 主动关闭这套做法可行，断流几乎即时（一个缓冲区），对同入站其他用户零影响
- **测量陷阱**（值得记住）：一开始用 `curl --limit-rate` 造长连接来测断流，结果显示「停用后还传了 30 秒」。实际是服务端早已全速把数据推完，客户端只是在慢慢读自己的缓冲，curl 迟迟才报错。改成**服务端按速率发送**（给流量源加 `rate` 参数）后数据才有意义。以后测这类时序，一律以服务端计数为准，不看客户端耗时
- 停用期间新连接是由追踪层直接关闭实现的；正式实现应该是主控把用户从入站配置里移除（V4 的内容），追踪层的拒绝只作兜底
