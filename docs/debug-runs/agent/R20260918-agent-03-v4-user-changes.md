# R20260918-agent-03 V4 增删用户时其他人是否断线

> 摘要：TCP 类协议（VLESS、AnyTLS、Shadowsocks）重建入站对在传的连接**完全无影响**，重建耗时 1–2 毫秒；Hysteria2（QUIC）一重建，所有在传会话立刻归零且不恢复，但新连接马上可用。另外确认 Shadowsocks 支持真正的热更新用户，不用重建。

- 状态：通过（结论明确，Hysteria2 需要在正式实现里做规避）
- 日期：2026-09-18；执行：Windows 开发机 / Claude Code 会话
- 关联：[原型计划](../../exec-plans/completed/2026-09-17-agent-core-prototype.md)，验证项 V4；开发轮次 D20260918-agent-03
- 代码：agent `71d8a4c`（增删用户），`11d513e`（修崩溃）
- 环境：测试 VPS，Debian 12 x86_64；sing-box 库 v1.14.1

## 目的

主控下发期望状态后，Agent 要改某个入站的用户列表。sing-box 通用的办法是按同一个 tag 先 `Remove` 再 `Create`。问题是：这会不会把该入站上其他用户正在进行的连接也打断？

## 做法

- 每个协议开两个用户（u1、u2）的下载，服务端按 3 MB/s 发送（客户端限速会得到假结果，见 R20260918-agent-02）
- 新增用户 u3（只重建该协议的入站），之后每 2 秒采样一次两个用户的计数增量，连续 6 秒；再删除 u3，同样采样
- 每 2 秒增量应约等于 6 MB；掉到 0 就说明连接被打断
- 另外单独验证：Hysteria2 重建后新连接是否可用；Shadowsocks 只调热更新接口、不重建，新用户能否连上

## 结果

每 2 秒的计数增量（正常值约 6016 KB）：

| 协议 | 变更前 | 新增后 2 / 4 / 6 秒 | 删除后 2 / 4 秒 | 下载进程 |
| --- | --- | --- | --- | --- |
| VLESS + REALITY | 5952 KB | 6016 / 6016 / 6016 | 6016 / 6016 | 存活 |
| AnyTLS | 5952 KB | 6016 / 6016 / 6016 | 6080 / 6016 | 存活 |
| Shadowsocks 2022 | 6016 KB | 6016 / 6080 / 6016 | 6016 / 6016 | 存活 |
| Hysteria2 | 5952 KB | **0 / 0 / 0** | 0 / 0 | 存活但无流量 |

重建耗时：TCP 类 1 毫秒，Hysteria2 2 毫秒（接口往返 2 毫秒）。

补充验证：

| 项 | 结果 |
| --- | --- |
| Hysteria2 重建后发起新连接 | u1、u2 都正常返回 |
| 新用户只加进列表、不重建 ss 入站 | 连接失败（退出码 52），说明入站确实还不认识他 |
| 调用 Shadowsocks 热更新接口后再连 | 成功，耗时 0 毫秒，且不影响已有连接 |
| `managed: true` 的 Shadowsocks 入站 | 启动失败：managed 模式不接受静态用户列表。**不开 managed 也能用热更新接口** |

## 结论

- **TCP 类协议可以随时重建入站**：VLESS、AnyTLS、Shadowsocks 上其他用户完全无感，1 毫秒完成
- **Hysteria2 不能随意重建**：QUIC 会话全部中断，而且不会自动续上（客户端要发起新请求才重连）。正式实现里要规避：把短时间内的多次用户变更合并成一次重建；停用用户靠追踪层即时断流（V3），不必立刻重建；真要重建时优先挑空闲时段
- **Shadowsocks 有更好的路**：`ManagedSSMServer.UpdateUsers` 能热更新用户，不用重建，0 毫秒且不影响任何连接。注意不要开 `managed` 选项，那会禁止配置里的静态用户列表
- 顺带修掉一个崩溃：`box.New` 把服务注册进 context 的服务注册表，注册表存在就复用；必须自己先建好注册表和 pause 管理器再传给 `box.New`，否则运行时调用 `InboundManager.Create` 会空指针崩溃
