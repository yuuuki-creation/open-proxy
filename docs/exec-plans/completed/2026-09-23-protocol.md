## 意外发现

- 发现：原设计里「版本不一致时暂停同步」会让流量上报也停下来，Agent 升级重启时，这段时间的流量全部丢失
  证据：architecture.md「流量上报」的计数在 Agent 进程里，重启归零
  影响：把 `TrafficReport` 列为稳定消息，版本不一致时照常上报（写进 protocol.md「兼容规则」）
- 发现：删除服务器后，Agent 会按本地状态一直提供代理，原设计没有处理
  证据：architecture.md「配置同步」里写明主控不可达时 Agent 继续服务
  影响：管理员决定删除时 Agent 自动卸载（protocol.md「删除服务器」）

## 决策记录

- 决策：两个方向各一个外壳消息，而不是一个外壳里混装两个方向的消息
  理由：生成的代码里，每一方只需要处理对方能发的消息，编译器帮忙检查
  日期：2026-09-23

## 结果与复盘

- 实现了：设计文档 protocol.md；`protocol/` 下三个 .proto（外壳、稳定消息、其他消息）和 `buf.yaml`；`.github/workflows/protocol.yml` 在指向 main 的 PR 上检查写法和兼容性
- 和目标相比：消息清单和规则都已定下，兼容检查自动化并验证过。代码生成还没接：Go 和 Rust 的生成放在 agent、panel 各自的计划里做，`go_package` 等语言相关选项到时用 buf 的 managed 模式设置，不写进 .proto
- 学到的：把整个流程串一遍才发现两个缺口：版本不一致期间流量上报会停（改成稳定消息）；删除服务器后 Agent 会一直提供代理（改成自动卸载）

## 现状与上下文

- 设计文档：`docs/design-docs/protocol.md`（消息清单、期望状态结构、兼容规则）；连接参数在 `architecture.md`「主控与 Agent 通信」
- 分支：协议定义归 main；panel、agent 通过合并 main 拿到 `protocol/`，生成的代码放在各自的代码目录，不进 main
- 术语：
  - **期望状态**：主控为一台服务器生成的整份配置（入站、用户、出口、证书），带版本号，Agent 自己算差异
  - **稳定消息**：版本不一致时仍然要能互相听懂的消息（Hello、升级、流量上报等），字段只加不改
  - **buf**：Protocol Buffers 的命令行工具；`buf lint` 查写法，`buf breaking` 和 main 上的旧版本比较，查出不兼容的改动

## 实施方案

先定设计再写 .proto：设计文档里的「待决定」会改变期望状态的字段（证书、失败项）和消息清单（`Uninstall`），先定下来可以少改一轮。.proto 分三个文件：外壳、稳定消息、其他消息。外壳要引用两边的消息，单独放一个文件，稳定消息的文件就不用依赖非稳定的。
