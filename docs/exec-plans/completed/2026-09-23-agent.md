## 目标与背景

原型（`prototypes/agent-core`，[计划](2026-09-17-agent-core-prototype.md)）证明了内嵌 sing-box、按用户计量、断连接、重建入站可行。现在写正式的 Agent `op-agent`：连上主控，按期望状态运行 sing-box 和 Mieru，上报流量，支持升级、回滚、卸载和 REALITY 目标检测。

做完后，一台 Linux 服务器执行面板给的安装命令，就能被主控管理：节点、用户、落地出口的任何变更自动生效，停用即时断流，流量每 10 秒上报。

## 意外发现

- 发现：sing-box 的路由规则只能在创建实例时给定，运行时不能增删。原设计「每个入站一条规则指向它的落地出口」在新增节点时做不到，除非重建整个实例（所有人断线）
  证据：v1.14.1 的 `adapter.Router` 只有查询规则的方法（`Rules()`），没有修改的方法
  影响：改用「分发」出站，见 architecture.md「落地出口」和「未验证的假设」
- 发现：Mieru 的 `Accept()` 返回连接和客户端的 socks5 请求后，还要由 Agent 回 socks5 应答，握手才算完成
  证据：`apis/server/interface.go` 的注释「Additional handshake is required with the returned proxy connection」
  影响：M5 里处理
- 发现：对方新版本才有的消息类型，解析后 `body` 为空，接收方分不清是请求还是推送，protocol.md 原来写的「不认识的请求回 ErrorReply」做不到
  证据：protobuf 解析时会丢掉不认识的 oneof 字段
  影响：改为不认识的消息一律忽略，请求方靠超时发现；ErrorReply「不支持」只用于认识但当前不能处理的请求（main 的 PR #4）
- 发现：sing-box 替换同 tag 的入站时，先建好并启动新的，成功后才关旧的。端口没变时，新入站会因为端口被旧的占着而起不来（没开 `reuse_addr` 就不设端口复用；未实测），只能先删旧的再建，这时新的建不起来节点就停了
  证据：v1.14.1 `adapter/inbound/manager.go` 的 `Manager.Create`；`common/listener` 只在 `reuse_addr` 为真时设 `SO_REUSEADDR` 和 `SO_REUSEPORT`
  影响：M3 在端口不变时先删后建，失败时节点停止并在失败原因里写明；做不到 protocol.md「应用规则」的「失败项保持原样」，该文档要求的「应用前校验」也还没做（技术债 agent-3）。2026-09-27 改为先校验、失败时按原来的配置建回去，见「决策记录」
- 发现：mieru 的 apis/server `Stop()` 会断掉所有已建立的连接，和它接口注释「Established network connections are NOT terminated」不一样。所以「改用户就停实例、起新实例」会让这个节点上所有人断线
  证据：v3.38.0 `apis/server/server.go` 的 `Stop` 调 `pkg/protocol/mux.go` 的 `Mux.Close`，后者关掉所有底层连接（underlay）
  影响：main 的 architecture.md「用户变更」注意事项和「未验证的假设」里「Mieru Stop() 后新实例能立即接管同一端口，旧连接继续传输」不成立，需要 main 更新；M5 改为直接用 mux、运行中换用户（见「决策记录」）
- 发现：mieru 服务端另外几处行为：监听默认设 SO_REUSEPORT；关 mux 时监听在另一个 goroutine 里异步关；关会话是逐个进行的，每个会话最多等 1 秒把关闭请求发出去，底层连接已断时一定等满；接收循环遇到任何 Accept 错误就退出，之后不再接新连接
  证据：v3.38.0 `pkg/sockopts/reuse_unix.go`、`pkg/protocol/mux.go`（`acceptUnderlayLoop`）、`session.go`（`closeWithError`）、`underlay_base.go`（`Close`）；调试记录 R20260927-agent-01 实测改密码重建那次应用用了 1.069 秒
  影响：M5 用自己的监听工厂（不设 SO_REUSEPORT、关实例时同步断开监听和底层连接、Accept 临时错误重试），mux 放到后台关
- 发现：mieru 只在建底层连接时认证用户：用户被删或改了密码以后，他已有的底层连接还能开新会话
  证据：调试记录 R20260927-agent-01（被删的用户 2 在旧底层连接上开的会话被分发出站拒绝）
  影响：被删的用户靠追踪层和分发出站拦住；改了密码必须重建实例，旧密码才会失效
- 发现：M3 比较节点时只比用户名单、不比凭据。重置凭据时用户名单不变，Agent 既不重建也不热更新，旧凭据一直有效
  证据：M3 的 `applyNode` 在「配置指纹和用户名单都没变」时直接返回
  影响：M5 改为连凭据（整条 User 的指纹）一起比，所有协议都受益
- 发现：在 systemd 服务里执行 `systemctl stop --no-block <本服务>`，systemctl 自己也在本服务的 cgroup 里，停止任务一开始它就和主进程一起收到 SIGTERM，返回「被信号结束」
  证据：调试记录 R20260927-agent-04
  影响：M7 把这种情况当作停止任务已经交给 systemd

## 决策记录

- 决策：分 8 个阶段，每个阶段从 agent 拉工作分支、开一个 PR，CI 通过再合并
  理由：按 git-workflow 的「PR 与编译」；阶段小，出问题容易定位
  日期：2026-09-23
- 决策：状态管理用一个 goroutine 顺序处理所有变更（期望状态、重建入站），其他 goroutine 只给它发请求
  理由：落实 architecture.md「一把锁串行化所有变更，重建入站的整个过程都在锁里」，并避开原型里「放锁后再重建」的问题
  日期：2026-09-23
- 决策：WebSocket 用 `github.com/coder/websocket`；nftables 用 `github.com/google/nftables`，不调用 `nft` 命令
  理由：前者 sing-box 已经依赖；后者纯 Go，不依赖系统里装没装 nft
  日期：2026-09-23
- 决策：protobuf 代码用 `buf generate` 加 buf 的远程插件 `protocolbuffers/go`（版本和运行库一致，v1.36.11），生成物提交在 `agent/internal/pb/`
  理由：开发电脑和 CI 不用装 protoc；插件版本固定，两边生成的结果一致，CI 能比对
  日期：2026-09-23
- 决策：配置文件的读取放在 `cmd/op-agent` 里，不单独建包
  理由：只有两个键，code-style.md 的目录表里也没有 config 包
  日期：2026-09-23
- 决策：`google.golang.org/protobuf` 固定在 v1.36.11，不用 `go mod tidy` 默认选的 v1.36.12
  理由：和生成插件、sing-box v1.14.1 用的版本一致；以后引入 sing-box 时也不会被抬高
  日期：2026-09-23
- 决策：收到 HelloResult 后，收消息的 goroutine 先停下，等 `OnConnected` 返回再处理后续消息
  理由：主控紧跟着 HelloResult 推送期望状态时，保证它不会在连接登记好之前被处理（否则应用完发 StateReport 会因为「没有连上」而丢掉）。代价是 `OnConnected` 里不能等主控回复，已写进接口注释
  日期：2026-09-23
- 决策：Agent 也每 30 秒 ping 主控，没回应就断开重连
  理由：主控那端已经不在的半开连接，只靠收消息发现不了
  日期：2026-09-23
- 决策：落地出口没建成功时，分发出站照样把节点的连接交给它，让拨号失败；绝不退回直连
  理由：退回直连，流量就会从错误的出口出去
  日期：2026-09-23
- 决策：状态管理的队列只留最新一份期望状态，还没处理的旧状态直接被新的替换
  理由：期望状态是全量的，只有最新一份有意义，中间的版本不必逐个应用
  日期：2026-09-23
- 决策：端口不变的重建，删旧入站之前先构造一遍新入站校验（不启动、不占端口），删旧建新失败时按原来的配置建回去（技术债 agent-3 的办法 2）；证书作为单独一项先校验，不通过时 TLS 节点接着用原来的证书
  理由：做到 protocol.md「应用规则」的「失败项保持原样」和「应用前校验」。没选「改文档，接受节点停止」：一份坏证书会让所有 TLS 节点一起停；没选「入站开 `reuse_addr` 让新旧并存」：并存时新连接会被内核分到两边，影响要实测才知道
  日期：2026-09-27
- 决策：Mieru 不用 apis/server，直接用 mieru 的 `pkg/protocol`（mux）；增删用户时运行中换用户列表（`SetServerUsers`），已有用户的密码和这个实例用过的不一样时才重建（包括被删后换了密码再加回来）
  理由：apis/server 改用户只能停实例重建，而停实例会断掉所有连接（见「意外发现」）；mux 能在运行中换用户，mieru 自己的 mita 重载配置也是这样做的。改密码必须重建，因为旧密码建立的底层连接还能开新会话。代价是依赖 mieru 的实现包而不是对外接口，升级 mieru 时要重新核对这几处（编译会报出接口变化）。main 的 architecture.md「Agent 内部」写的是 apis/server，需要 main 改
  日期：2026-09-27
- 决策：mieru 用 v3.38.0（计划写的是 v3.37.0）
  理由：v3.38.0 是 2026-09-24 发布的最新版，和 v3.37.0 的差别在 UDP 传输的会话和 mita 的转发，我们用到的 mux 接口、apis/client 没变；两者都要求 protobuf v1.34.2，不会抬高 v1.36.11
  日期：2026-09-27
- 决策：Mieru 支持 CONNECT 和 UDP ASSOCIATE，BIND 回「不支持」。CONNECT 的应答等出站连上目标后再回（sing 的 `LazyConn`，失败时回对应的错误码）；UDP 先回成功，再按第一个包的目标地址路由，UDP 包在同一个会话里传（格式同 mieru 的 PacketOverStreamTunnel）
  理由：mieru 客户端只发这两种命令，mita 也不支持 BIND；做法和 sing-box 自己的 SOCKS 入站一样
  日期：2026-09-27
- 决策：用户列表为空的 Mieru 节点照样启动，放一个随机密码的占位用户（用户名 0）
  理由：mux 没有用户就启动不了；其他协议的节点没有用户时也照常监听，保持一致
  日期：2026-09-27
- 决策：运行验证用的工具放在 `agent/test/`（假主控 `fakemaster`、Mieru 客户端 `mieruclient`、脚本 `scripts/`），和 Agent 同一个模块，CI 一起检查，不随 Agent 发布
  理由：能直接用 Agent 的 protobuf 代码；code-style.md 的目录表里没有这个目录，需要 main 补上
  日期：2026-09-27
- 决策：Agent 退出时先等状态管理的 goroutine 停下，再关 sing-box 和 Mieru
  理由：只有这个 goroutine 改它们（Mieru 的实例表没有锁），退出时不能并发
  日期：2026-09-27
- 决策：端口跳跃的规则是 `meta nfproto ipv4 fib daddr type local udp dport <范围> redirect to :<端口>`，一个节点一条，放在 inet 表的一条 nat 链（prerouting、dstnat 优先级）里；每次应用整体重建：先加再删表、再建表链规则，在一次提交里完成，没有规则时只删表
  理由：只转发往本机的 IPv4 包，经过本机转发的（容器等）不动；整体重建最简单，也能纠正被别人改过的规则；原子提交保证失败时原来的规则不变
  日期：2026-09-27
- 决策：端口跳跃转到节点实际在跑的端口；范围不合法、和别的节点的范围重叠（节点 ID 小的优先）、盖住别的节点的端口、这个节点的 Hysteria2 入站没在跑时，只有这个节点报 `ITEM_PORT_HOPPING`
  理由：节点的新配置没应用成功、还在用旧端口时，转到旧端口才对；主控分配端口时本来就会避开这些冲突，Agent 再检查一遍，免得一个节点的错误把别的节点的流量转走
  日期：2026-09-27
- 决策：不做 nodes.md 写的「没有 nftables 时用 iptables」
  理由：google/nftables 直接走 netlink，不需要系统里有 nft 命令，只要内核支持；inet 族的 nat 要内核 5.2 以上，现在常见的发行版都满足。没有时这一项报失败，面板上能看到。需要 main 改 nodes.md
  日期：2026-09-27
- 决策：google/nftables 沿用依赖图里已有的版本 v0.2.1-0.20240414091927-5e242ec57806，不升到 v0.3.0
  理由：它是 sing-box 经 tailscale 间接依赖的，升版本会跟着改 tailscale 用的版本，可能编译不过；这个版本的功能够用
  日期：2026-09-27
- 决策：新加命令行参数 `-nft-table`（默认 `op_agent`）；没有本地状态时启动就清掉以前留下的表
  理由：测试 VPS 的规则只允许动测试专用的表 `open_proxy_test`；有本地状态时第一次应用会整体重建，没有时也要把上次留下的规则清掉
  日期：2026-09-27
- 决策：升级包的 Ed25519 签名是对整个二进制文件内容签的（`ed25519.Verify(公钥, 文件内容, 签名)`），SHA-256 另外单独校验；公钥编译时用 `-ldflags "-X main.upgradePublicKey=<标准 base64>"` 注入，为空时回失败「没有内置升级验签公钥」
  理由：按 protocol 里 `Upgrade.signature` 的定义（主会话确认过）；签整个文件不依赖摘要算法
  日期：2026-09-27
- 决策：下载地址只用自己配置的主控地址拼（路径必须以 `/` 开头，拼出来的主机和协议不能变），Token 放 `Authorization: Bearer`，不跟随跳转，上限 256 MiB、4 分钟
  理由：protocol.md「升级」要求 Token 不发到别处；跟随跳转可能把请求带到别的地址
  日期：2026-09-27
- 决策：替换前检查新二进制是本机架构的 ELF，并在旁边试跑 `-version`，报的版本号必须等于目标版本；同一个版本不升级
  理由：签名只能保证是官方的包，保证不了主控没发错架构；新版本在这台机器上根本起不来的话，它也没法自己回滚
  日期：2026-09-27
- 决策：升级标记 `upgrade.json` 记 `from`、`to`、`started_at`、`starts`，替换前写好。启动时版本等于 `to` 是试运行（`starts` 加一，超过 3 次直接回滚）；不等于 `to` 说明上次升级没生效（回滚了或替换前中断了），Hello 里报 `rolled_back_from`；通过认证后删标记。回滚是把 `.bak` 改名回来（标记留给旧版本报告），然后退出由 systemd 拉起。试运行时限 3 分钟
  理由：architecture.md「发布、安装与升级」；中断和回滚用同一个规则处理，不用另外的状态
  日期：2026-09-27
- 决策：连接层的 `Handler` 加 `AfterReply`：升级、卸载在回复发出之后再补发流量上报、退出
  理由：protocol.md 要求先回复再补发流量上报；回复由连接层发，处理函数自己不知道什么时候发完
  日期：2026-09-27
- 决策：卸载时 Agent 自己停入站、删 nftables 表、删二进制和 `.bak`、配置文件（目录空了才删）、数据目录里自己的文件（目录空了才删）；从 `/proc/self/cgroup` 找到自己所在的服务，disable、删 `/etc/systemd/system` 下的服务文件并 `daemon-reload`，最后 `systemctl stop --no-block` 再等 SIGTERM。没用 systemd-run 起临时单元
  理由：`--no-block` 只是把停止任务交给 systemd，停止由 systemd 执行，不会半途而废，比临时单元简单；只删自己的文件，免得参数指错时误删；服务是被明确停止的，`Restart=always` 不会再拉起
  日期：2026-09-27
- 决策：升级和卸载同一时间只做一件；升级成功后不再接受新的升级、卸载请求（马上退出）
  理由：两件事都要替换或删除二进制，并发会互相破坏
  日期：2026-09-27
- 决策：REALITY 检测：每个目标先解析一次（有 IPv4 优先），再握手 3 次（SNI 是目标域名，ALPN h2、http/1.1）；证书按系统根证书和主机名自己验证、不中断握手；TLS 1.3、H2、证书有效要每次成功的握手都满足才算，延迟取中位数（TCP 连接加 TLS 握手，不含 DNS）；单个目标的问题写进它的 `error`；最多 32 个目标、8 个并行、50 秒内完成
  理由：负载均衡后面的机器可能不一样，取最保守的结果；证书无效时也要能报 TLS 版本和 ALPN；主控等 1 分钟。R20260927-agent-06 发现延迟里含了 DNS 查询，才改成先解析
  日期：2026-09-27
- 决策：REALITY 扫描：只扫 IPv4 网段，一次最多 4096 个地址；并发数默认 4、上限 32，速率默认每秒 4 个、上限 50；按速率或按最坏情况（每个地址都等到 5 秒超时）算超过 18 分钟就直接拒绝；连 443 端口不发 SNI，合格条件是 TLS 1.3、H2、证书里有不带通配符的域名；按延迟排序一次性返回；同一时间只做一个扫描；整体失败回 `ErrorReply`
  理由：nodes.md 要求慢速、低并发；主控等 20 分钟，扫到一半才超时会白扫，先拒绝更清楚；通配符域名不能直接当 SNI；扫描结果还要由管理员选中后再检测
  日期：2026-09-27
- 决策：`internal/reality/` 放检测和扫描
  理由：code-style.md 的目录表里没有这个目录（`agent/test/` 也没有），需要 main 补上；本分支不改 main 的文件
  日期：2026-09-27

## 实施方案

Agent 内部的组成和数据流：

1. 启动：读配置 → 检查升级标记（M7）→ 读本地保存的期望状态 → 按它启动 sing-box 和 Mieru → 连主控 → 开始定时上报
2. 收到 `DesiredState`：先存盘，再交给状态 goroutine 逐项应用，应用完发 `StateReport`
3. 逐项应用的顺序：
   1. 更新追踪层的放行名单，并断开被移除的用户（停用即时生效，不等后面的步骤）
   2. 出站：新增、参数变化的 `exit-<ID>` 按 tag 重建；更新分发出站的「节点 → 出口」表
   3. 证书：校验通过才换上；不通过报失败，TLS 节点接着用原来的证书
   4. 节点：新增的建入站；删除的移除；端口或协议参数变化的重建（端口没变时先校验、再删旧建新，失败时按原来的配置建回去，见「决策记录」）；只有用户变化时，Shadowsocks 走热更新，其他协议重建（Hysteria2 只在有用户新增时重建，只删用户靠第 1 步已经够了）；证书变化时 TLS 节点重建
   5. 节点都处理完，再删除不用的出口
   6. 自建落地的 SOCKS5 入站和来源 IP 名单（端口没变的重建同节点）
   7. 端口跳跃规则（M6）
   8. 每一项的失败都记下来，不影响其他项
4. 流量上报：每 10 秒从追踪层取计数快照，读网卡，发 `TrafficReport`
