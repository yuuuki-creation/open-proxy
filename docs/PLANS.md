# ExecPlan 编写规范

ExecPlan（执行计划）是一份**边做边更新**的设计兼实施文档。目标：一个没有任何聊天上下文的人或 AI 代理，只读这份计划和当前代码，就能理解要做什么、做到了哪一步，并把它做完。

## 什么时候写

- 新功能、较大重构、涉及多个模块的改动
- 预计一次会话做不完的任务
- 有多种方案需要权衡取舍的任务

改几行、修个小 bug 不需要写。

## 文件与生命周期

- 路径：`docs/exec-plans/active/YYYY-MM-DD-简短英文标识.md`，例如 `2026-09-17-add-http-forwarding.md`
- 分支：计划建在它要改的内容所属的分支上，之后只在这个分支上修改，见 [git-workflow.md](git-workflow.md)。main 上也可以有计划，用于协议定义、跨多个会话的设计工作
- 完成时：填写「结果与复盘」，状态改为「已完成」，移到 `docs/exec-plans/completed/`
- 放弃时：在「结果与复盘」写明原因，状态改为「已放弃」，同样移到 `completed/`

## 写作要求

- **自包含**：不依赖聊天记录或只存在于外部链接里的信息；需要的背景、术语、文件路径都写进计划。
- **始终反映真实状态**：每完成一个步骤、每改变一次方案，立即更新，不要攒到最后。
- **可验证**：验收标准具体到能执行的命令和预期结果，而不是「功能正常」。
- **记录为什么**：方案变了，在「决策记录」里写清楚原因。
- **摘要在最前**：标题下第一段是 1–3 行摘要（当前进度 + 最重要的结论），每次更新进度时同步改写。别人只读前 15 行就知道这份计划到哪了。
- **不堆细节**：每轮调试的过程和数据写进 `docs/debug-runs/`，计划里只链接和写结论。

## 模板

````markdown
# <动词开头的简短标题，如：实现 HTTP 转发>

> 摘要：当前进度和最重要的结论，一到三行。

- 状态：进行中
- 分支：main / panel / agent
- 创建：YYYY-MM-DD
- 最后更新：YYYY-MM-DD

## 目标与背景

要解决什么问题、给谁用、做完后能做到什么以前做不到的事。

## 进度

- [x] (YYYY-MM-DD HH:MM) 已完成的步骤
- [ ] 未开始的步骤
- [ ] 部分完成的步骤（已完成：…；剩余：…）

## 意外发现

实施中遇到的意外行为、坑、性能问题等，附简短证据（报错、日志、测试输出）。

- 发现：…
  证据：…

## 决策记录

- 决策：…
  理由：…
  日期：YYYY-MM-DD

## 结果与复盘

阶段完成或全部完成时填写：实现了什么、还差什么、与最初目标相比如何、学到了什么。

## 现状与上下文

相关代码在哪里、现在怎么工作、关键术语的含义。假设读者对这个仓库一无所知。

## 实施方案

整体思路：按什么顺序改哪些模块，为什么这样做。

## 具体步骤

要执行的命令、要修改的文件，以及每一步预期看到的结果。

## 验证与验收

怎么证明做完了：运行什么命令、访问什么地址、预期输出是什么。

## 可重复执行与回滚

哪些步骤可以安全地重复执行；出错时怎么回到安全状态。

## 接口与依赖

新增或修改的接口、函数签名、配置项，以及引入的第三方依赖和选择理由。
````
